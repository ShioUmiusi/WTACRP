## 1. 数据来源与许可

位置与属性表的 **位流布局与帧格式移植自** `wrpl-inspector`（Go，**AGPL-3.0**，v3 分支，
<https://github.com/maxsupermanhd/wrpl-inspector>，作者 flexcoral）：

- `wrpl/packet/packetReader.go` —— 包帧（2 字节头 + 可选 u32 毫秒时间戳）
- `wrpl/danet/bitStream.go` —— `BitReader` / `ReadCompressed` / 位序（**MSB-first**）
- `wrpl/packet/parser/fm/fm.go` —— `fm` 解析器（`ptype=2`）：`BitReader` 逐位读取 + 字节对齐 + 各子块
- `wrpl/packet/parser/movement/main.go`、`inspector/tabs/mapview/mapview.go` —— 用于定位"位置来自哪个解析器"
- `inspector/tabs/mpipackets/names.go` —— MPI 消息号 → 名称（用于认领 `0xD04A`）

`tools/wrpl_decode.py` 是按这些实现**重写的 Python 版**，未逐字照抄；本地只读副本在
`build/wrpl-inspector/`。**交付内容里不复制该项目的代码文本**。

8111 数据（`data/raw/rb-session/`）**只用于开发期校验**，不进入 `tracks.json` / `own_props.json` 的任何字段。

## 2. 包帧与时间轴

```
VLQ 长度前缀 S
body = 之后的 S 字节
body[0] 的 bit4(0x10) 置位 -> 类型 = body[0]^0x10，沿用上一条时间戳，包头 2 字节
否则                      -> 类型 = body[0]，包头 6 字节：body[1] 恒 0x00，body[2:6] = u32 LE 毫秒
载荷 = body[2:] 或 body[6:]
```

- **毫秒口径**：`ts_ms = u32 LE @ body[2:6]`。全部 86773 个包合计消耗 14180794 B，零残余。
- **原始计数器口径**（`tracks.json` 采用）：`tickRaw = ts_ms × 256`，`secPerTick = 3.90625e-06`，
  `sec = tickRaw / 256000`。两套编号比值恒为 256（独立复算已发现该差异，本文件统一用 raw）。
- 回放自身：7.822 s（StartMarker）→ 589.949 s（EndMarker）。`fm` 数据覆盖 31.10–589.84 s。
- **不存在需要拟合的时间偏移**。`align` 里的 `tx/ty` 只是与 8111 的平移残差，供校验用。

## 3. 位置通道：`ptype=2` → `fm` 解析器

`fm.go` 的 `ParsesMatching()` 是 `{2: nil}`——**捕获全部 `ptype=2` 包**。一个包是一个位打包的**条目列表**：

```
循环：
  hasUID = 1 bit
  hasUID ? uid = ReadCompressed() & 0x7FF : uid++      # uid = 实体 id（11 位）
  uid == 0x7FF -> 结束
  noData = 1 bit；置位 -> 本条只有 uid，跳过
  ... Unk0/1/2、u32、Unk5、ZigZag 三元组表 ...
  PosX = f32(4B) / PosY = f32(4B) / PosZ = f32(4B)
  EulerBytes = u32（紧凑欧拉角：航向/俯仰/滚转各 10/9/10 位 + 3 个符号位）
  Unk12 = u32 → AlignToByteBoundary → 7 B → 引擎表 → 传感器表 → 干扰弹表 → 目标表 → 两个可选尾块
```

`euler` 的低位可用 `unpack_euler()` 解出航向（弧度），本机可用它交叉校验 8111 `compass`。

**为什么之前的搜索全都失败**：载荷是**位流**，条目的长度随内容变（因为有可变长子表），
所以"固定字节偏移上的 float"一定找不到；而同一个包内**多条 entry** 意味着"同一 uid 的时间序列"
要先把 entry 循环补全才能拿到。这些成功全部来自**逐行移植参考实现**，不是猜出来的。

本局统计：`ptype=2` 共 2330 个包，载荷 43 B–5173 B；解出 **52074 条位置、44 个 uid**，
**44 个 uid 全部连续**（无 NaN、无解析异常），采样率约 4 Hz。

## 5. 击杀事件

`ptype=4` 签名 `00 02 58 58 f0` = **0xF058 TextKillReport**，共 **33 个**，与 8111 hudmsg 的 33 条
"击落/击毁"逐条对齐（格式解析用 28 对做时间标定，MAD 0.10 s）。

字段按 **`IdFieldSerializer32`**（`wrpl/idfieldserializer/`）位流解码，本工具已移植（`decode_kills_full`）：

```
[u16 LE sizeTableOffset][varint fields 位掩码] -> 跳到 sizeTableOffset 读各字段位宽 -> 回到正文
字段：1 KillerPid u32 / 2 PlayerVehicle 字符串 / 3 VictimUid u16&0x7FF /
      4 KillerUid u16&0x7FF / 0xA PlayerWeapon 字符串 / 0xB VictimPid u32 / 0xC DestroyedWeapon 字符串
```

**33/33 全部解出，零失败**（killerUid 含本机 368；`killerUid=2047=0x7FF` 表示坠毁/环境击杀，无击杀者）。
本工具解出的 33 条与格式解析独立实现的 `kill_events.json` **逐字段一致**（两条独立实现互证）。

产出 `tracks.json.killPositions[]`（**新增字段，未改动任何既有字段**）：

```jsonc
{ "tickRaw": …, "victimUid": 361, "killerUid": 372, "victimPid": 0, "killerPid": 28,
  "killerVehicle": "su_25", "weapon": "su_r_60",
  "victimPos": [x, y, z]|null, "killerPos": [x, y, z]|null,
  "hasVictimPos": true, "hasKillerPos": true }
```

取法：在 `ptype=2` 的 fm 航迹里查该 uid **不晚于** `tickRaw` 的最近采样（4 Hz，容差 2 s）——
不能往未来取，因为受击者死亡后 uid 可能立刻被复用（见下）。
**33 条里受击者有坐标 30 条、击杀者有坐标 32 条**；缺的几条受击者是地面/AI 单位（uid 215/216/299），
不在 fm 通道里。本机（uid-368）的 2 次击杀：tick 51533056（201.3 s，victim 348）、
tick 144747520（565.4 s，victim 374）。

**一个必须知道的坑：uid 会复用**。受击者航迹的末采样中位比击杀 tick 晚 **15.2 s**（p90 4.0 s），
说明 uid 在该实体死亡后被别的实体复用；`units[]` 里相邻采样速度 >600 m/s 的 **16 步**就是这些接缝。
**渲染时应在这些点断开航迹**，否则会出现瞬移。`tracks.json.limits` 里已写明。

**未做**：致命伤 `0xF056`（32 条）与重伤 `0xF157`（15 条）——格式解析已解出
（`kill_events.json`），可与之串成"致命伤 → 击杀"的因果链，本文件不重复。


## 6. 搜索空间：试过什么、排除了什么（如实记录）

在走通移植路线之前，穷尽过下列空间，**全部为空**（这也是最终必须靠移植的原因）：

1. **帧/时间基**：先误以为时间戳是 1/256 刻度、并沿用前人的 `rate=256472/offset=54.024`；
   实测纠正为"毫秒 + 原始计数器 = ms×256"，且**时长逐位吻合内嵌 `timePlayed`**，因此时间轴不拟合。
2. **字节对齐字段扫描**（float32/float64/int32/uint32/int16/uint16 × 全字节偏移）：
   - 对 `ptype=2` 的 00f0/00f8 族、`ptype=6` 的 0020/0022/0024/0025/0026 族、`ptype=4` 的全部 4 字节签名族；
   - 同时用**值相关**与**导数相关**（抗未知平移/缩放），目标 = 8111 本机 x/y/高度；
   - 最好只有 R²≈0.25–0.77，**全部判为不相干**（这些高值来自平滑序列的伪相关）。
3. **位级定长搜索**：12/14/16/18/20/22/24/28/32 位、有符号/无符号、全位偏移，覆盖包头与载荷前 16 B；最高相关 0.573。
4. **"同长度组"假设**：按载荷长度分组，假设同长度组的布局一致——逐位活跃度图显示变长子表导致
   活跃区不固定，且长度与 8111 同刻可见机数**不相关**（corr −0.135），该假设排除。
5. **`movement` 解析器**：参考实现的匹配条件（载荷 `[0]=0xff [1]=0x0f [4/5]=a3 f0 …`）
   **在本局全部 86773 个包、任何 base 偏移 0..8 下都零命中**——该消息本局未出现（属别的协议版本消息）。
   其"LEB128 id + 3×f64"算法用"轨迹连续性"自校验扫描全偏移也**无命中**。
6. **`0003584a`（本机属性表）里没有水平位置**：76 个属性与本机 X/Y 相关全部 <0.44；
   包头 9 B 的位级扫描最高 0.573。**结论：本机水平位置只在 `ptype=2` 的 fm 载荷里。**
7. **`00035843`（= 0xD043 ReplayCameraParams）不是位置通道**：载荷 = 头 + 四元数（|q|=1）+ 9 个 float，
   任何字节/位偏移都不与本机 X/Y/H 相关 → 是相机参数，已排除。
8. **ECS `0024`** 确实是 `pos(3)+quat(4)+vel(3)`（本机无关），用"载荷长度 − 114"定位块起点覆盖 887/1066，
   但它**不含本机**（44 个 uid 与本机高度序列的最近匹配 rms 4443 m 起，最好的 uid-368 走的是 fm 通道）。
9. 击杀/伤害包、`00025856/57`、`000358xx` 等族的身份映射、地面单位 `0xF073 GroundModelPositions`：
   本文件未收口（见下）。

## 10. 三条独立验证 + 侧别争议（重要）

### 10.1 三条互相独立的验证，结论一致

| # | 验证 | 结果 | 独立性 |
|---|---|---|---|
| 1 | 本机航迹 vs 8111 `map_obj` 的 **`icon=Player`** 位置（身份无歧义） | 平面 rms **3.98 m** / 高度 rms **0.45 m** | 用 8111 |
| 2 | 每条 fm 航迹的**切线方向** vs 8111 同一接触的 **`dx/dy` 方向**（本机：中位差 ~2°） | 位置帧与运动方向自洽 | 用 8111 的方向，不用颜色/身份表 |
| 3 | **击杀时受击者与击杀者的距离** | p50 **1353 m**、max **4392 m**、**86.2% < 3 km**（n=29） | **完全回放内部**，不用 8111 |

第 3 条最关键：空对空导弹的杀伤距离就是公里量级；如果 uid 标签或位置解错，victim↔killer 距离会均匀散布到
几十公里。实测 p50 1.35 km / max 4.4 km 基本不可能是巧合。**它同时验证了 uid 标签、位置、以及 `killPositions`。**

### 10.2 8111 的 `compass` 与 `map_obj` 的 `dx/dy` 互不一致（真正原因见 §10.4）

本机实测：`euler+90` 与 8111 的 **`compass`**（仪表罗盘）中位圆误差 **0.1°**；
但 `euler+90` 与 8111 的 **`dx/dy`（地图航向）** 中位差约 **120°**，而**航迹切线与 `dx/dy` 只差约 2°**。
→ 说明 8111 的 `indicators.compass` 与 `map_obj` 的 `dx/dy` 在本局**互不一致**（差距随时刻变，28°–122° 都出现过）。
**原因见 §10.4：`map_obj` 的 y 是屏幕轴（向下=南）**，所以 `dx/dy` 给出的是屏幕方位而不是罗盘方位。
**最终结论：交付坐标用 `y = +PosZ`（北）；航向取航迹切线方向 = 回放 `euler` 航向 = 8111 `compass`。**

### 10.3 阶段性质疑：`uid_map.side` 曾与两条独立证据矛盾（已由 §10.5 闭合，保留留痕）

### 14.3 弹药发射点：已解出，并经本文件独立复核（`projectile_launches.json`）

ECS 解析更正了此前的「弹药位置未解」：**位置其实解出来了**，之前误判有两个原因——
① 按模板整体扫一个偏移，把 block 长度变体互相污染（**按 block 长度分组后，每个变体的四元数 |q|≈1 命中率都是 100%**：

但自洽只说明它内部没矛盾；真正把它钉住的是外面三条不同来源的证据（8111 颜色、8111 可见性、结算玩家表）。
反过来，`side_final` 的 2 色图内部也自洽，却在一条 TK 边上翻了色——**两条自洽路径冲突时，要去找第三条判据，而不是比谁的样本多。**
